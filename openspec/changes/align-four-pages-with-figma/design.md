## Goals / Non-Goals

**Goals:** создать измеряемый визуальный контракт и применить его через существующие компоненты; обеспечить согласованность общих элементов и сохранение интерактивных состояний.

**Non-Goals:** новая архитектура, смена библиотек, изменение фактических данных ради совпадения с демонстрационными числами, подключение реальных платежей/авторизации, редизайн без источника, публикация сайта. Любые изменения личного кабинета исключены из задачи.

## Decisions

### 1. Новый источник и журнал соответствия

Перед UI-правками получить полноценный design context для конкретных фреймов и видимых дочерних блоков; sparse-ответ не использовать как готовую спецификацию. Зафиксировать в отчёте route → node ID → viewport → состояние → screenshot → замечания. Для каждого блока записать измерения сетки, шрифтов, отступов, радиусов, теней и ассетов. Старый файл использовать только как исторический материал. Альтернатива — настройка по старому аудиту или визуальной памяти — отклонена: она закрепит расхождения.

Ограничение MCP View seat сейчас не позволяет получить эти данные. Задачи извлечения остаются открытыми до восстановления доступа или предоставления эквивалентных подробных экспортов. Не подменять неизвестные значения догадками. Браузерное сравнение допустимо для инвентаризации, но не подтверждает полную точность.

### 2. Сначала общие элементы, затем локальные различия

Проверить существующие tokens, assets, зависимости и компоненты. Использовать общие токены, HeaderNav и SiteFooter для публичных страниц; AccountHeader сохранить отдельным. Главная содержит собственную разметку футера: согласовать её со стилями SiteFooter, объединять только если содержимое и поведение эквивалентны. Коррекции локальных композиций размещать в существующих page/module CSS. Альтернатива — три независимые копии стилей — создаёт повторные расхождения.

Не удалять тени и полупрозрачность массово. Подтверждать каждую правку конкретным слоем. Обновление старого design contract должно быть явным и точечным; не отключать проверки ради прохождения нового оформления.

### 3. Последовательность страниц

- Главная: RoadNetworkHero, ServicesGrid, LoyaltyRail, NewsGrid, ImportantStories, MediaGallery, ContactsTabs, StatisticsBlock, последующие блоки и футер. Проверить все секции, не ограничиваться hero.
- Компания: app/about/page.tsx, page.css, AboutVideo и HistoryMapOverlay. Сверить светлую цитату, видеопостер, дату, показатели, сетки деятельности/структуры/комплаенса и контакты. Сохранить проверенные назначения ссылок.
- Пользователи: app/road-users/page.tsx, RoadUsersHero, RoutePlanner, соответствующие CSS modules. Убрать отдельную сетку ServicesGrid из потока между hero и калькулятором; составить соответствие каждого её назначения существующему быстрому действию или меню, чтобы ничего не потерять. Сохранить расчёт, промежуточные точки, перестановку и работу карты. Правила проезда сверить с изображениями и геометрией макета.

Альтернатива — полная замена страниц сгенерированной статической разметкой — отклонена из-за потери сценариев.

### 4. Ассеты и адаптив

Сопоставить каждый статический asset со слотом Figma и локальным файлом; скачивать оригиналы разрешённым workflow, не хранить временные URL. Не использовать скриншот страницы как asset реализации. Динамические данные и медиа остаются динамическими. Использовать точные мобильные фреймы при наличии; отсутствующие варианты адаптировать из desktop с записью решения. Не отображать направляющие Figma как часть оформления.

### 5. Проверка соответствия

Снимать до/после на одинаковых ширинах и состояниях: desktop 1920, контроль 1440, 768, mobile 375/390 плюс действующая viewport-матрица harness. Для трёх публичных страниц проверить всю высоту, делать парные изображения или overlay по секциям; временно стабилизировать анимацию/видео только в тестовом режиме. Проверить загруженные шрифты и локальные ассеты. Завершение требует отсутствия необъяснённых расхождений композиции и измеряемых токенов; различия растеризации, динамических данных и необходимые accessibility-отклонения перечислить отдельно. Автоматический screenshot pass сам по себе не является визуальной приёмкой. Обновление snapshot-baseline — отдельное явное действие после human review.

## Risks / Trade-offs

- Недоступны точные параметры Figma → завершить извлечение до зависимых UI-правок; не заявлять pixel-perfect результат.
- Пересечение с fix-responsive-overflow → перед apply проверить его актуальное состояние, согласовать ownership CSS и повторно использовать проверки переполнения; не архивировать соседний change автоматически.
- Общие стили меняют соседние маршруты → после общего слоя проверять все три публичных маршрута, ограничивать селекторы.
- Изменение порядка сервисов влияет на доступность действий → составить таблицу старых/новых точек входа и проверить назначения.
- Документация и harness привязаны к старым node IDs → обновить явное соответствие новому источнику, сохранив функциональные и accessibility-контракты.

## Migration Plan

Миграции данных не нужны. Начать с инвентаризации источника и проверки ветки, затем общие компоненты, страницы и адаптив. Все изменения выполняются в общей ветке; preview остаётся http://localhost:3001, без перезапуска общего сервера. Проверки harness запускать последовательно, функциональные прогоны отдельно от @visual. Для общих файлов необходим harness:changed; визуальные сценарии на Windows включают все @visual. Публикация и изменение screenshot-baselines не выполняются автоматически. Откат при необходимости ограничивается файлами/патчами этого change, без reset рабочего дерева и удаления чужих артефактов.
